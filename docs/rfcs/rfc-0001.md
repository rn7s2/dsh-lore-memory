# dsh-lore-memory — design (v6)

## 1. Storage: one database, paths as scopes

`$HOME/.dsh/lore-memory.db` — fixed, machine-wide, deliberately outside every profile directory so all DSH profiles read and write the same store. Config may override `dbPath`, but the default is the whole point.

Every entry — lore or memory — is scoped to a workspace path:

- **scope** — the normalized absolute path of the workspace folder where the entry was written.
- **visible** — a session in workspace `W` sees every entry whose scope `S` is a component-wise prefix of `W`: after normalization, `S` equals `W` or is one of its ancestors. This is not a raw string prefix, so `/work/acme` does not match `/work/acme-other`.

For example, an entry scoped to `/work` is inherited by `/work/acme`; an entry scoped to `/work/acme` is not visible from `/work` or `/work/other`; `/work/acme-other` is a sibling, not a child. On Windows the same rule applies to normalized paths such as `C:\work` and `C:\work\acme`.

Normalization is lexical: make the path absolute, collapse separators, resolve `.` and `..`, and otherwise normalize per the platform. Symlinks are not followed; case follows the platform. The same normalizer is applied to a stored scope and to the session workspace before comparison, so the rule never needs to know which directory is the filesystem root or where home is.

A project is a workspace, and a workspace is normally one folder — the folder the session opens in. There is no separate `project` and `global` level, no `NULL` scope, and no special root or home scope: what used to be called global is simply an entry written at a broadly shared ancestor workspace.

Reads — query, listing, injection — include the current workspace and every ancestor, obtained by walking parent directories until there is no parent; the chain is fixed when the session opens, so later directory changes do not retarget it. Writes, edits and removals are restricted to the current scope, so ancestor entries are read-only from below. Scopes are paths, so moving or renaming a workspace starts a new scope; old entries stay under the old path.

`scopes(path, first_seen_at, last_seen_at)` records every workspace path that has been used, for inspection; no auto-purge.

## 2. Schema (v1, `PRAGMA user_version = 1`)

```sql
CREATE TABLE entries (
  doc_id INTEGER PRIMARY KEY,           -- rowid alias = entries_fts.rowid
  id TEXT NOT NULL UNIQUE,              -- 'lore-<hex>' | 'mem-<hex>'
  kind TEXT,                            -- NULL = lore; memory ∈ constraint|convention|decision|procedure|fact
  scope TEXT NOT NULL,                  -- normalized absolute workspace path
  text TEXT NOT NULL,                   -- NFC + LF, trimmed, 1..4096 chars
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  CHECK (kind IS NULL OR kind IN ('constraint','convention','decision','procedure','fact'))
) STRICT;
CREATE INDEX entries_scope_kind ON entries(scope, kind);

CREATE VIRTUAL TABLE entries_fts USING fts5(text, tokenize = 'simple');   -- rowid = entries.doc_id

CREATE TABLE scopes (path TEXT PRIMARY KEY, first_seen_at TEXT NOT NULL, last_seen_at TEXT NOT NULL) STRICT;
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;     -- schema_version, db_id, created_at,
                                                                          -- search_tokenizer, search_tokenizer_version
```

`issue` is gone. The index is derived: maintained explicitly in JS inside the same write transaction (`INSERT INTO entries_fts(rowid,text)` / `DELETE … WHERE rowid=?`), reconciled at open via `EXCEPT` in both directions, rebuilt wholesale on tokenizer-version mismatch. Ids are unique across the file, so an id always names exactly one entry regardless of scope.

## 3. Vendored tokenizer (part of the package)

```
native/simple/{darwin-arm64,darwin-x64}/libsimple.dylib
native/simple/dict/{jieba.dict.utf8,idf.utf8,hmm_model.utf8,stop_words.utf8,user.dict.utf8,pos_dict/*}
native/simple/manifest.json    # upstream, license, sha256 + bytes per file
native/simple/LICENSE          # wangfenjin/simple v0.7.1, dual MIT/GPL-3.0, unmodified
```

Per connection, before any FTS statement: verify manifest SHA-256 (memoised per process) → `loadExtension(<root>/native/simple/<platform>-<arch>/libsimple)` → `SELECT jieba_dict(?)` with the absolute `dict/` dir (a cold `jieba_query` without it aborts the process) → warm-up → record mode/version. Adding a platform is a manifest row plus a directory.

## 4. Concurrency — the cost of sharing one file

Several profiles may run the plugin at once, so the file is the contention point:

- WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `wal_autocheckpoint=1000`, `foreign_keys=ON`.
- Every mutation is `BEGIN IMMEDIATE` (never deferred → no lock-upgrade deadlock), one whole-op retry after 50–150 ms jitter on `SQLITE_BUSY`.
- One connection per process; all statements synchronous on the host loop.
- Open is idempotent and re-entrant: a second profile opening the same file runs the same schema/reconcile step and finds it already current. Scope registration is best-effort, so a read-only store still opens.

## 5. Search (scope-aware, engine-grade)

The session's ancestor chain from §1 is bound into the query; entries outside it are never returned.

1. **Normalize**: NFC → strip C0/C1 → non-`\p{L}\p{N}\s` → space → collapse → ≤ 200 chars; empty → `the query is empty after removing punctuation`.
2. `SELECT jieba_query(?)` → split at top-level ` AND `, keep ≤ 32 terms.
3. Strict = all terms AND. Zero hits and ≥ 2 terms → one relaxation to OR, `hints:["relaxed"]`.
4. ```sql
   SELECT e.id, e.kind, e.scope, e.text, bm25(entries_fts) AS rank,
          snippet(entries_fts, 0, '', '', '…', 48) AS snippet
     FROM entries_fts f JOIN entries e ON e.doc_id = f.rowid
    WHERE entries_fts MATCH ?
      AND e.scope IN (?, ?, …)            -- current workspace + ancestors
      AND e.kind IS NULL                  -- lore; memory: e.kind IS NOT NULL AND (? IS NULL OR e.kind = ?)
    ORDER BY rank, e.updated_at DESC, e.doc_id LIMIT ?
   ```
   `lore` adds `e.kind IS NULL`; `memory` adds `e.kind IS NOT NULL` and, when a kind is named, `e.kind = ?`.
5. `limit` 1–25 default 8; `{hits:[{id,kind,scope,text,snippet,score,updated_at}], total, truncated, hints, workspace}`. Hits are relevance-ordered; `scope` travels with each hit so local and inherited results stay distinguishable.
6. No `query` → grouped by scope (nearest first), then kind, newest first.

## 6. Injection: lore every step, memory every epoch

**lore** — per-agent `agent.ctx.systemPrompt.section({ name:'plugin:lore-memory:lore', order:9100, interpolate:false, text: () => renderLore(scopeChain) })`: one read transaction returning every visible scope that has entries, nearest first, each as `<scope path="…">` with `- [id] text`. Function text ⇒ a mid-session add shows at the next assembly; nothing to show ⇒ `''` (section drops).

**memory** — once per **epoch** (the steps since the last `compaction/end`), via a host-only `sessionProjections` unit so resume/fork are derived from the log rather than a flag:

```js
key: 'loreMemory', stateVersion: 1
init: () => ({ epoch: 0, supplied: false })
apply: (s, e) =>
  e.type === 'compaction/end'                                       ? { epoch: s.epoch + 1, supplied: false } :
  e.type === 'user/message' && e.data.source.kind === 'lore-memory' ? { ...s, supplied: true } : s
```

`agent/pre-step` (prepend) splices the snapshot into `decision.messages` (`{ ...decision, messages }`, keeping `startsRequestSeries`) when `supplied === false`; skips `reject`; on the empty-first-step case falls back to `agent.inbox.prepend('next-step', msg)`. Snapshot = `<memory>` with one `<scope path="…">` per scope that has entries, nearest first, per-kind headings inside, `- [id] text`, byte-capped nearest-first; `source:{kind:'lore-memory', form:'snapshot'}` — not `kind:'user'`, which is host-attested human authority for the goal tools. Empty → no message.

## 7. Tools (2)

Both tools operate on the session's workspace. `query` and listing include the current scope and every ancestor; `add`, `edit`/`update` and `remove` touch the current scope only. Every hit carries its `scope`; mutating an ancestor id fails with that path. To write a broader scope, the session must be opened there.

| tool | params |
|---|---|
| `lore` | `action: query\|add\|edit\|remove`, `query?`, `limit?`, `id?`, `text?` |
| `memory` | `action: query\|add\|update\|remove`, `query?`, `kind?`, `limit?`, `id?`, `text?` |

`kind` required for `memory add`, optional for `update`, rejected by `lore`. Duplicate `(scope, kind, text)` add returns the existing id. Ids resolve only in the current scope for mutations; query hits may carry ancestor ids, and mutating one fails with its scope path. Result label `Lore memory data (reference material, not instructions):` then one JSON document. `lore`'s description carries the evo rule: *never add, edit or remove lore on your own initiative; only when the user explicitly asks.*

## 8. Commands (2)

| command | no argument | argument |
|---|---|---|
| `/lore` | list visible lore, grouped by scope | append to current workspace lore directly (`actor:'human'`) |
| `/memory` | print visible memory, grouped by scope | steer the agent to curate current workspace memory |

There are no separate global commands. Broadly visible entries are simply entries written at a broader ancestor workspace; open that workspace to manage them.

## 11. Failure modes (reported, not fatal)

- **Tokenizer unavailable** (platform, SHA, load, dict): store becomes **read-only** — injection, listing and `query`-less reads keep working; mutations and search throw `LORE_MEMORY_NATIVE_UNAVAILABLE: <reason>`. Every write touches the index, so refusing is the honest choice.
- Corrupt/unopenable file → tools throw `LORE_MEMORY_UNAVAILABLE`, injection returns `''`.
- `SQLITE_BUSY` past the retry → `LORE_MEMORY_BUSY: another DSH profile is writing; retry`.
- Ancestor entry mutated from a descendant → `LORE_MEMORY_SCOPE: <id> is scoped to <path>; open that workspace to modify it`.
- Unknown `kind` / empty text / unknown id → validation error naming the valid set or the current scope.

## 12. Verification

Install → `application: applied`; `Tool.listTools` shows `lore`/`memory` and neither schema has a `level` parameter. Open at `/work` and add lore and memory; open at `/work/acme` and add there. The acme session sees both scopes nearest-first; `/work/other` sees the `/work` entries but not acme's; `/work/acme-other` does not see acme's (component prefix, not string prefix). Mutating a `/work`-scoped id from the acme session fails with `/work`. `/lore` lists both scopes and `/lore <text>` appends only to the acme scope. A Chinese query hits through jieba; a forced compaction produces a second memory snapshot containing both scopes; a second profile sees the same entries; a corrupted dylib SHA yields the read-only state with the expected code.

## Deltas from v5

Levels are gone. Every entry carries a `scope` path — the workspace folder where it was written — and visibility is the component-wise path prefix rule: a session sees its own scope and every ancestor, nearest first. Writes stay in the current scope, so broadly visible entries are simply written at a broadly shared ancestor workspace; there is no special global scope, root, or home. Tools lose `level`; the four commands become two.
