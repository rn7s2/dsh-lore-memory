# RFC 0001: dsh-lore-memory (v10)

## 1. Goal

A DSH plugin that gives the agent two kinds of persistent notes, kept per workspace:

- **Lore**: rules the user wants followed in a workspace, such as "use pnpm, never npm". Lore changes only when the user asks. The model sees the current lore every turn.
- **Memory**: knowledge the agent keeps for itself (constraints, conventions, decisions, procedures, facts). The agent curates it freely. The model sees it once, when an agent starts.

Both can be searched, and Chinese works as well as English. Only macOS is supported.

## 2. Scopes

Every entry belongs to the workspace folder it was written in, called its **scope**.

A session sees the entries of its own workspace and of every parent folder. The match is on whole path components, so `/work/acme` sees `/work`, but `/work/acme-other` does not see `/work/acme`.

| entry scope | seen from `/work` | seen from `/work/acme` | seen from `/work/acme-other` |
|---|---|---|---|
| `/work` | yes | yes | yes |
| `/work/acme` | no | yes | no |

- There are no levels and no special global scope. To make something visible broadly, write it in a broad parent workspace.
- A session writes to its own workspace by default. A tool call may name another workspace explicitly, which must be the session's workspace or one of its parent folders: an agent can write broadly, but never sideways, and it cannot reach into a child or sibling workspace.
- A workspace is identified by its real path (symlinks resolved), compared exactly and case-sensitively, so a symlinked path to a parent folder is the same scope.
- A subagent uses its parent session's workspace for both reading and writing, wherever its own working directory is.
- Moving a folder starts a new scope. Old entries stay under the old path.

## 3. Storage

One SQLite database per machine, shared by every DSH profile. A profile may point to its own database instead.

The database holds the entries and a full-text index over them, and the two are kept in step on every write. Entries have no size limit.

Several DSH processes may use the database at once. A write that finds the database busy retries briefly without blocking the host, and fails with a "busy, try again" error after about 5 seconds.

## 4. Search

Search uses the vendored `simple` tokenizer (jieba segmentation plus pinyin), shipped inside the package.

- A query matches entries containing **any** of its terms. `bm25` ranks the results, so entries matching more terms, and rarer terms, come first.
- The goal is recall. Prefix matches (`test` finds `testing`) and pinyin matches between English and Chinese are intended.
- Results only include entries visible from the session, and each result shows its scope.
- A call without a query lists all visible entries, nearest scope first.

## 5. How notes reach the model

A request is laid out as the system prompt, then the history, then the newest input. While a session runs, the plugin never changes anything already sent, so the prompt cache stays valid.

- **Memory** goes into the system prompt once, when the agent's system prompt is first built. It survives compaction. For newer memory mid-session, the agent uses the `memory` tool.
- **Lore**: a fresh copy is inserted every turn, after the history and just before that turn's new input. Earlier copies stay where they are. Lore written by another session in the same workspace therefore shows up at the next turn.

This applies to every agent, subagents included. The two are clearly labelled as lore (rules for this workspace) and memory (what the agent remembers), grouped by scope, nearest first.

## 6. Tools

- **`lore`**: query, add, edit, remove.
- **`memory`**: query, add, update, remove. Every entry has a kind.

Rules:

- Tool results are presented as reference knowledge: not a direct instruction for the current task, but guidance on how to do related work.
- Both tools take an optional `workspace`: an absolute path that is the session's workspace or one of its parent folders. A change lands in that scope instead of the session's workspace. Omitted, changes land in the session workspace, as before. `query` takes no `workspace`: it already covers the session workspace and its parents.
- Any change the agent makes to lore must be approved by the user through the host's approval prompt, and the prompt names the workspace that will change.
- Exception: in a Full Access session (no sandbox and no approval prompts), the user has chosen to let the agent act without asking, so agent changes to lore apply directly.
- When approval prompts are off but the session is not in Full Access, the agent cannot change lore at all. The refusal says so and points the user to `/lore`.
- Memory changes need no approval.

## 7. Commands

| command | without argument | with argument |
|---|---|---|
| `/lore` | list visible lore | add the text as lore in this workspace (no approval needed: the user typed it) |
| `/memory` | list visible memory | ask the agent to update this workspace's memory accordingly |

`/lore` only adds, by design. To edit or remove lore, the user asks the agent and approves the change.

## 8. Config

- `dbPath`: database location. Defaults to `~/.dsh/lore-memory.db`, shared by all profiles.
- `searchLimitDefault`: number of results when a query gives no limit. Defaults to 8.

## 9. Failure behaviour

Failures are reported; none of them breaks the session.

- **Tokenizer unavailable**: the store becomes read-only. Listing and injection still work; search and writes fail with the reason.
- **Database unavailable**: the tools fail, and nothing is injected.
- **Database busy for too long**: the write fails with "busy, try again".
- **Changing an entry from a parent workspace without naming it**: refused, and the message says which `workspace` to pass instead.
- **Naming a workspace that is neither the session's nor a parent folder**: refused, and nothing is changed.
- **Naming a workspace with a relative path**: refused, with the reason.

## 10. Acceptance

- Visibility follows the table in §2, and a change lands in the session's own workspace unless it names a parent folder.
- Changing a parent workspace's entry without naming it is refused; naming it works, for lore behind the usual approval.
- A workspace that is neither the session's nor a parent folder is refused, for lore and memory alike.
- A change to lore requested by the agent shows an approval prompt. Rejecting it writes nothing.
- In a Full Access session, an agent change to lore applies without a prompt.
- A Chinese query finds Chinese entries.
- Memory appears once and is still there after compaction.
- Every turn carries the current lore, including lore just added from another session in the same workspace.
- A second DSH profile sees the same entries.
- A tampered tokenizer leaves the store read-only, with the reason reported.
- The page lists every entry at and below a path prefix, and edits an entry in any scope, including a parent folder.
- Page writes need no approval and are recorded as user edits.

## 11. Web page

The Web GUI adds one sidebar entry, **Lore & Memory**, directly below **Automation tasks**, and one page for every scope.

- A breadcrumb over absolute path prefixes starts at **All scopes** (the filesystem root). The child folders of the selected prefix are listed with the entry counts of their whole subtree.
- Two tabs, **Lore** and **Memory**, list every entry stored at or below the selected prefix, and show the counts for that prefix.
- Entries can be added, edited, and deleted in place. Memory entries also choose a kind. A new entry lands in the selected folder, which defaults to the current prefix.

The page is the user's surface. It addresses an entry by its owning scope path, so it can change any scope directly, including a parent folder, without the agent's approval step. It writes with `author = user` and needs no approval, because the user performed the action. The agent's tools keep their own rules in §6, including the optional named workspace and the lore approval.

The two halves share one specification in `src/remote.ts`. The Host registers the five operations (`overview`, `entries`, `create`, `update`, `delete`) in the Typert registry and provides the matching Service under `loreMemory`; the browser mounts the same descriptors and calls `ctx.remote.loreMemory`. Every browser-supplied field passes a strict codec on the Host, and a store failure reaches the page with its code and reason.

A degraded store is reported, never hidden: `read-only` disables writes, and `unavailable` also skips the listing.

## Changes in v10

- Adds the Web management page and its `loreMemory` Remote namespace. Session behaviour and storage are unchanged.

## Changes in v9

- `lore` and `memory` take an optional `workspace`: an absolute path that must be the session's workspace or one of its parent folders. The change lands there, so an agent can record something in a broad parent workspace from a narrower session. Omitted, changes still land in the session workspace.
- The refusal for a parent-scope entry now says which `workspace` to pass instead of telling the user to open a session there.

## Changes in v8

- In Full Access sessions, agent changes to lore apply without approval. With approval prompts off in any other mode, they are still refused, with a reason that names `/lore`.

## Changes in v7

- Lore moved out of the system prompt. A fresh copy is inserted every turn, just before the new input.
- Memory is injected once, in the system prompt.
- Agent changes to lore require the user's approval.
- Search matches any term and ranks by `bm25`.
- Busy writes retry briefly instead of failing at once.
- macOS only, no size limits, and only two config settings.
- Implementation detail (SQL, pragmas, hook names, package layout) moved out of the RFC.
